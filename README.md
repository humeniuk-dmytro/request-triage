# Тріаж вхідних запитів AI-юніту

Читає вивантаження інбоксу (`input_requests.csv`), проганяє кожен запит через
LLM і повертає структуру, з якою вже можна працювати: категорія, відділ,
пріоритет, суть, конкретні дії та питання на уточнення. На виході — `output.json`,
звіт з агрегатами і таблиця для Google Sheets.

```
input_requests.csv
        │
        ├─ читання й валідація рядків ──────────► проблемні рядки в лог
        │
        ▼
   обробка запиту  (async, з обмеженням темпу під квоту провайдера)
        │
        ├─ Gemini зі схемою відповіді + temperature 0
        ├─ розбір JSON → нормалізація → строга валідація Pydantic
        ├─ невалідно? один repair-виклик із текстом помилки
        └─ усе одно невалідно? запис зі статусом failed — рядок не втрачено
        │
        ▼
   другий прохід: пошук дублів між запитами (один виклик на весь файл)
        │
        ▼
   out/output.json   out/report.md   out/output.csv
        │
        └─ опційно: Google Sheet, дайджест у Telegram
```

## Швидкий старт

### Подивитись, як воно працює — без ключа й без мережі

```bash
uv sync
uv run triage --provider fake
```

`fake` — це детермінований класифікатор на ключових словах. Він потрібен не
заради якості, а щоб конвеєр можна було прогнати цілком, нічого не налаштовуючи:
з'являться всі три файли в `out/`. Ним же працюють тести й CI.

### Реальний прогін

```bash
cp .env.example .env          # і вписати GEMINI_API_KEY
uv run triage
```

Безкоштовний ключ: <https://aistudio.google.com/apikey> — картка не потрібна,
окремий ключ від замовника теж.

### Docker

```bash
docker build -t request-triage .
docker run --rm --env-file .env -v "$PWD/out:/app/out" request-triage
```

### Корисні прапорці

| Прапорець | Навіщо |
|---|---|
| `--provider fake` | прогін без ключа й без мережі |
| `--limit 3` | перевірити на трьох рядках, не витрачаючи квоту |
| `--rpm 0` | зняти обмеження темпу (платний тір) |
| `--no-dedupe` | пропустити другий прохід |
| `--notify` | надіслати підсумок у Telegram |
| `--sheets` | записати результат у Google Sheet |
| `-v` | докладний лог, разом із логами SDK |

Повний список — `uv run triage --help`.

## Що на виході

- **`out/output.json`** — усі запити з витягнутими полями, технічним слідом
  обробки (`meta`) і паспортом прогону (`manifest`: модель, хеш промпту, токени,
  вартість, час).
- **`out/report.md`** — агрегати по категоріях, пріоритетах, відділах і каналах;
  окремо — що потребує реакції сьогодні, що потребує уточнення (з готовими
  питаннями), можливі дублі та збої обробки.
- **`out/output.csv`** — той самий зріз таблицею. Імпортується в Google Sheets
  одним `Файл → Імпорт`.

Один запис `output.json`:

```json
{
  "id": "REQ-005",
  "channel": "Telegram",
  "timestamp": "2026-06-08T11:05:00",
  "raw_text": "ГОРИТЬ. Сьогодні до вечора треба вивантажити список усіх контрагентів…",
  "extraction": {
    "reasoning": "Разове вивантаження даних із явним дедлайном на сьогодні.",
    "category": "звіт/аналітика",
    "target_department": "бухгалтерія",
    "priority": "high",
    "short_summary": "Терміново потрібен список контрагентів з витратами понад 50к за травень.",
    "requested_actions": ["вивантажити список контрагентів з витратами понад 50к за травень"],
    "needs_clarification": false,
    "clarification_questions": [],
    "confidence": "high",
    "mentioned_systems": []
  },
  "possible_duplicate_of": null,
  "meta": {
    "status": "ok", "failure_kind": null, "attempts": 1, "repairs": 0,
    "model": "gemini-2.5-flash", "prompt_tokens": 1502, "output_tokens": 180,
    "latency_ms": 2310, "error": null
  }
}
```

## Схема

Обов'язкові поля — з ТЗ, дослівно. `category` приймає рівно шість значень:
`автоматизація`, `інтеграція`, `звіт/аналітика`, `баг/підтримка`,
`питання/консультація`, `поза скоупом`.

### Чим схему розширено і навіщо

| Поле | Навіщо |
|---|---|
| `clarification_questions` | `needs_clarification: true` без питань — марний прапорець: він каже, що робота стоїть, і не каже, що з цим робити. Тут — готові питання, які координатор одразу пересилає замовнику. Перевіряється правилом валідації: прапорець без питань не проходить. |
| `reasoning` | Одне речення, чому саме ця категорія й пріоритет. Дві користі: рішення моделі можна перевірити, не перечитуючи оригінал, і сама якість класифікації вища — поле генерується **першим** (`propertyOrdering` у схемі), тобто модель аргументує до того, як обере відповідь. Дешевий ланцюжок міркувань усередині структурованого виводу, без окремого виклику й без увімкненого thinking. |
| `confidence` | Дає з чим працювати там, де таксономія об'єктивно на межі (REQ-016: «відповіді асистента не по темі» — це баг чи очікувана поведінка RAG?). Низька впевненість — кандидат на людський перегляд, а не тихо прийняте рішення. Це ж робить розділ про недетермінізм нижче конкретним. |
| `mentioned_systems` | Google Ads, PlanFix, BigQuery, Meta, Slack — сигнал маршрутизації: за системою видно, яка команда володіє задачею. Витягується тим самим викликом, тобто безкоштовно. |
| `possible_duplicate_of` | REQ-013 дослівно повторює REQ-001 («той самий звіт по Google Ads, що Оля просила в понеділок»). Дублі — головне джерело подвійної роботи в спільній черзі. Заповнюється **окремим проходом**: у порядковому виклику модель бачить рівно один запит і про інші не знає в принципі. |

Чого свідомо **не** додано: `is_actionable`. Його повністю покриває
`category: "поза скоупом"` разом із порожнім `requested_actions` — і REQ-008
(«дякую, все працює»), і REQ-012 (закупівля ноутбука) розкладаються без нього.
Кожне зайве поле — це токени в кожному запиті й ще одна поверхня, на якій модель
може помилитись.

## Що станеться, коли модель поверне сміття

Це не гіпотеза — на цьому будувалась уся обробка. Драбина знизу вгору:

1. **Обмеження на рівні API.** `response_mime_type: application/json` +
   `response_schema` — модель обмежена ще до генерації, вигадати назву категорії
   чи пропустити поле вона не може.
2. **Толерантний розбір.** Огорожі ` ```json `, проза навколо об'єкта —
   зрізаються.
3. **Нормалізація до валідації.** `"Автоматизація"` → `автоматизація`,
   `"HIGH "` → `high`, `"так"` → `true`, рядок замість списку → список із одного
   елемента, `"невідомо"` → `null`. Валідне-але-неохайне не має коштувати
   платного виклику.
4. **Строга валідація Pydantic**, включно з семантичними правилами, яких не
   виражає JSON-схема: прапорець уточнення зобов'язаний мати питання, і навпаки.
   Зайві поля заборонені — якщо модель дописала своє, вона імпровізує, і це
   сигнал, а не шум.
5. **Один repair-виклик.** Моделі повертається її ж відповідь і дослівний текст
   `ValidationError` — вона виправляє конкретне порушення, а не гадає.
   Кількість спроб — `TRIAGE_MAX_REPAIRS`, за замовчуванням 1: друга спроба
   рідко допомагає там, де не допомогла перша, і подвоює вартість.
6. **Запис зі статусом `failed`.** Рядок зберігається цілком, з оригінальним
   текстом і поясненням у `meta.error`, і окремою секцією потрапляє у звіт.
   **Прогін не падає, дані не зникають.**

Транспортні збої (429, 5xx, таймаут) обробляються принципово інакше: це
випадковість, яка лікується повтором того самого запиту. Витримка береться з
відповіді сервера, якщо він її назвав, інакше — експонента з джитером.
Плутати ці два класи помилок дорого: повторювати невалідний вивід безглуздо,
а «лагодити» промптом вичерпану квоту неможливо.

Перевірено тестами — `tests/test_extractor.py`, `tests/test_ratelimit.py`.
На живій моделі це не тестується: вона ламається тоді, коли їй заманеться, а не
коли ми запускаємо тести.

## Де рішення ламається

### Квота провайдера — найжорсткіше обмеження

Безкоштовний тір `gemini-2.5-flash` — **5 запитів на хвилину**. Перший реальний
прогін цим і закінчився: 14 з 18 запитів впали, бо семафор паралельності
обмежує *одночасність*, а квота рахує запити *за хвилину*. Це різні речі.

Закрито обмежувачем частоти (`TRIAGE_RPM`, за замовчуванням 4 — запас 20%, бо
рівно на межі провайдер усе одно віддає 429). Ціна: 18 запитів обробляються
близько 5 хвилин замість 20 секунд. Для інбоксу, який зараз розбирають руками,
це прийнятно; для чогось інтерактивного — ні.

Що зробити при більших обсягах: платний тір (ліміт зростає на порядки),
`gemini-2.5-flash-lite` (вищий ліміт, дешевше, гірша якість на межових
формулюваннях), або Batch API, який для несинхронної обробки інбоксу підходить
краще за все.

### Обсяг

18 рядків — не навантаження. Що зламається на 10 000 на добу:

- **Немає стану.** Кожен прогін обробляє файл заново. Повторний запуск — це
  повторна оплата тих самих запитів. Потрібна ідемпотентність: хеш `raw_text` як
  ключ і кеш результатів.
- **Немає черги.** Один процес, один файл, усе в пам'яті. Реально потрібен
  воркер, який читає з черги й пише в БД, а не CLI поверх CSV.
- **Прохід по дублях не масштабується.** Зараз усі саммарі йдуть в один
  контекст — на тисячах запитів це не влізе. Правильно: ембединги + пошук
  найближчих сусідів, а LLM лише підтверджує кандидатів.
- **Обробка невідновлювана.** Прогін, обірваний на 900-му рядку, починається
  з нуля. Потрібен чекпоінт після кожного запису.

### Недетермінізм

`temperature: 0` прибирає варіативність з боку клієнта, але **не гарантує**
однаковий вивід: провайдер не обіцяє відтворюваності, а на межових
формулюваннях різниця в одному токені змінює категорію. Реальний приклад із
цих даних — REQ-016 («чи нормально, що асистент іноді відповідає не по темі»):
це `баг/підтримка` чи `питання/консультація`, залежить від трактування.

Чим закрито:
- `confidence` у кожному записі — межові випадки видно в даних, а не здогадкою;
- `reasoning` — видно, на чому саме будувалось рішення;
- `prompt_sha256` у маніфесті — якщо два прогони розійшлись, одразу видно, чи
  змінювався промпт;
- правила розведення категорій і тай-брейкери прописані в промпті явно —
  найбільше розкиду дає саме «автоматизація vs звіт/аналітика».

Чим **не** закрито: немає розміченого набору й метрики якості. Без них «стало
краще» — це відчуття, а не факт. Це перше, що я зробив би далі.

Порядок величин: приблизно 1 500 вхідних токенів на запит (більшість —
системний промпт із таксономією) і 150–250 вихідних. Тобто вартість майже цілком
визначається промптом, а не текстом запиту.

Звідси й напрямки економії: кешування системного промпту (він незмінний і
становить основну частину входу), коротший промпт ціною якості, дешевша модель,
або відсів очевидного до LLM — порожні тексти вже відсіюються без виклику.
`reasoning` і `confidence` теж коштують токени; я вважаю їх вартими того, і в
цьому можна не погодитись — цифри вище дозволяють порахувати.

### Дані йдуть у зовнішній API

Тексти запитів разом із внутрішньою кухнею (назви систем, відділів, підрядників)
відправляються в Google. Для тестового завдання це нормально, для впровадження
потрібно щонайменше свідоме рішення: угода про обробку даних, або маскування
чутливого до відправки, або локальна модель. У коді цього немає, і робити вигляд,
що питання не існує, не варто.

### Дрібніше

- **Промпт-ін'єкція.** Текст запиту загорнутий у `<request_text>` із прямою
  вказівкою трактувати вміст як дані. Це знижує ризик, але не знімає: інбокс —
  недовірене джерело, і хтось може написати туди що завгодно.
- **Google Sheets** перезаписує аркуш цілком. Для знімка інбоксу це правильно,
  для журналу змін — ні.
- **Мова.** Промпт і таксономія українською. Запит англійською класифікується
  нормально (REQ-006), але вивід усе одно буде українською.

## Що зробив би далі

1. **Розмічений набір і метрика.** 50–100 запитів з еталонними мітками, скрипт
   заміру accuracy по категорії й пріоритету. Без цього будь-яка правка промпту —
   зміна наосліп.
2. **Ідемпотентність і кеш** за хешем `raw_text`. Дешево, а прибирає повторну
   оплату й робить прогони порівнюваними.
3. **Ембединги для дублів** замість одного контексту з усіма саммарі.
4. **Веб-хук замість CSV** — приймати запити зі Slack і Telegram напряму, писати
   в БД, віддавати чергу через API.
5. **Автоматичне заведення задач** для запитів із високою впевненістю, і
   черга на людський перегляд для решти — `confidence` для цього вже є.

## Розробка

```bash
uv sync              # залежності
uv run pytest -q     # 64 тести, без мережі й без ключа
uv run ruff check .  # лінтер
```

```
src/triage/
├── models.py        # уся схема: вхід, контракт LLM, вихід, нормалізація
├── prompt.py        # промпти, правила таксономії, схема відповіді для API
├── extractor.py     # обробка одного запиту: драбина валідації та repair
├── pipeline.py      # читання CSV, паралельна обробка, запобіжник
├── dedupe.py        # другий прохід: дублі між запитами
├── report.py        # агрегати та три вихідні файли
├── cli.py           # точка входу
├── llm/             # base (контракт) · gemini · fake · ratelimit
└── integrations/    # telegram · sheets
```

Тести не ходять у мережу: усе через `FakeClient`, який або рахує за евристикою,
або віддає наперед задані відповіді, зокрема навмисно зіпсовані. CI ганяє лінтер,
тести й наскрізний прогін на `--provider fake` — без ключів і без бюджету.

Ключі беруться лише з оточення, `.env` у `.gitignore`.
