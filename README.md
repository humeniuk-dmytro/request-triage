# Тріаж вхідних запитів AI-юніту

[![CI](https://github.com/humeniuk-dmytro/request-triage/actions/workflows/ci.yml/badge.svg)](https://github.com/humeniuk-dmytro/request-triage/actions/workflows/ci.yml)

> **English summary.** A Python CLI that turns each request from an inbox export (CSV) into structured data —
> category, department, priority, summary, actions and clarifying questions — using Gemini structured output,
> strict Pydantic validation and one repair call on invalid output. A second LLM pass finds duplicate requests.
> Outputs JSON, a Markdown report and CSV; optional Google Sheets and Telegram integrations; offline tests and
> GitHub Actions CI. The rest of this README is in Ukrainian.

Читає вивантаження інбоксу (`input_requests.csv`), проганяє кожен запит через
LLM і повертає структуру, з якою вже можна працювати: категорія, відділ,
пріоритет, суть, конкретні дії та питання на уточнення. На виході — `output.json`,
звіт з агрегатами і таблиця для Google Sheets.

```
input_requests.csv
        │
        ├─ читання й валідація рядків ──────────► проблемні рядки в лог
        │
        ▼
   обробка запиту  (async, з обмеженням темпу під квоту провайдера)
        │
        ├─ Gemini зі схемою відповіді + temperature 0
        ├─ розбір JSON → нормалізація → строга валідація Pydantic
        ├─ невалідно? один repair-виклик із текстом помилки
        └─ усе одно невалідно? запис зі статусом failed — рядок не втрачено
        │
        ▼
   другий прохід: пошук дублів між запитами (один виклик на весь файл)
        │
        ▼
   out/output.json   out/report.md   out/output.csv
        │
        └─ опційно: Google Sheet, дайджест у Telegram
```

## Швидкий старт

### Подивитись, як воно працює — без ключа й без мережі

```bash
uv sync
uv run triage --provider fake
```

`fake` — це детермінований класифікатор на ключових словах. Він потрібен не
заради якості, а щоб конвеєр можна було прогнати цілком, нічого не налаштовуючи:
з'являться всі три файли в `out/`. Ним же працюють тести й CI.

### Реальний прогін

```bash
cp .env.example .env          # і вписати GEMINI_API_KEY
uv run triage
```

Безкоштовний ключ: <https://aistudio.google.com/apikey> — картка не потрібна,
окремий ключ від замовника теж.

### Docker

```bash
docker build -t request-triage .
docker run --rm --env-file .env -v "$PWD/out:/app/out" request-triage
```

### Корисні прапорці

| Прапорець | Навіщо |
|---|---|
| `--provider fake` | прогін без ключа й без мережі |
| `--limit 3` | перевірити на трьох рядках, не витрачаючи квоту |
| `--rpm 0` | зняти обмеження темпу (платний тір) |
| `--no-dedupe` | пропустити другий прохід |
| `--notify` | надіслати підсумок у Telegram |
| `--sheets` | записати результат у Google Sheet |
| `-v` | докладний лог, разом із логами SDK |

Повний список — `uv run triage --help`.

### Опційні інтеграції

Обидві вимикаються прапорцем і жодна не має права завалити прогін: результат уже
записаний на диск, а розсилка — це доставка, не обробка. Немає креденшелів —
крок пропускається з попередженням. Обидві перевірені на живих креденшелах,
а не тільки на моках (`tests/test_integrations.py` перевіряє саме те, що вони
не валять прогін).

**Telegram** (`--notify`): `TELEGRAM_BOT_TOKEN` від @BotFather і
`TELEGRAM_CHAT_ID`. Зроблено на `httpx`, без aiogram: тут немає бота, який
слухає апдейти, — є один POST, і тягнути заради нього фреймворк немає сенсу.

**Google Sheets** (`--sheets`): service account, JSON-ключ у
`GOOGLE_SERVICE_ACCOUNT_FILE`, id таблиці в `GOOGLE_SHEET_ID`.

Про права окремо, бо це найчастіша помилка в такій інтеграції. Service account —
**окрема особа з власним порожнім Drive**: доступ до конкретної таблиці дає не
скоуп, а шеринг цієї таблиці на його email. Тому скоуп за замовчуванням рівно
один — `spreadsheets` (`GOOGLE_SCOPES`, якщо потрібне інше), і жодних IAM-ролей
у проєкті. Ключ, який живе у файлі поруч із кодом, має відкривати один аркуш і
нічого більше; ширші права не додають можливостей, а лише збільшують те, що
втрачається разом із файлом.

Аркуш перезаписується цілком одним `update` замість рядок-за-рядком: прогін
тріажу — це знімок інбоксу на момент часу, а дописування створило б таблицю, де
той самий запит лежить у трьох станах і незрозуміло, який актуальний.

## Що на виході

- **`out/output.json`** — усі запити з витягнутими полями, технічним слідом
  обробки (`meta`) і паспортом прогону (`manifest`: модель, хеш промпту, токени,
  вартість, час).
- **`out/report.md`** — агрегати по категоріях, пріоритетах, відділах і каналах;
  окремо — що потребує реакції сьогодні, що потребує уточнення (з готовими
  питаннями), можливі дублі та збої обробки.
- **`out/output.csv`** — той самий зріз таблицею. Імпортується в Google Sheets
  одним `Файл → Імпорт`.

Один запис `output.json` — як є, з реального прогону:

```json
{
  "id": "REQ-005",
  "channel": "Telegram",
  "timestamp": "2026-06-08T11:05:00",
  "raw_text": "ГОРИТЬ. Сьогодні до вечора треба вивантажити список усіх кон…",
  "extraction": {
    "reasoning": "Просять терміново зробити вивантаження даних звітного характеру з дедлайном на сьогодні через запит бухгалтерії.",
    "category": "звіт/аналітика",
    "target_department": "бухгалтерія",
    "priority": "high",
    "short_summary": "Терміново вивантажити список контрагентів з витратами понад 50к за травень.",
    "requested_actions": ["вивантажити список контрагентів з витратами понад 50к за травень"],
    "needs_clarification": false,
    "clarification_questions": [],
    "confidence": "high",
    "mentioned_systems": []
  },
  "possible_duplicate_of": null,
  "meta": {
    "status": "ok", "failure_kind": null, "attempts": 1, "repairs": 0,
    "model": "gemini-3.5-flash-lite", "prompt_tokens": 1800, "output_tokens": 147,
    "latency_ms": 61165, "error": null
  }
}
```

Вхідні поля лежать поряд із витягнутими навмисно: людина на чергуванні бачить
першоджерело поруч із висновком моделі й не мусить лізти назад у CSV.

## Схема

Обов'язкові поля — з ТЗ, дослівно. `category` приймає рівно шість значень:
`автоматизація`, `інтеграція`, `звіт/аналітика`, `баг/підтримка`,
`питання/консультація`, `поза скоупом`.

### Чим схему розширено і навіщо

| Поле | Навіщо |
|---|---|
| `clarification_questions` | `needs_clarification: true` без питань — марний прапорець: він каже, що робота стоїть, і не каже, що з цим робити. Тут — готові питання, які координатор одразу пересилає замовнику. Перевіряється правилом валідації: прапорець без питань не проходить. |
| `reasoning` | Одне речення, чому саме ця категорія й пріоритет. Дві користі: рішення моделі можна перевірити, не перечитуючи оригінал, і сама якість класифікації вища — поле генерується **першим** (`propertyOrdering` у схемі), тобто модель аргументує до того, як обере відповідь. Дешевий ланцюжок міркувань усередині структурованого виводу, без окремого виклику й без увімкненого thinking. |
| `confidence` | Задум: низька впевненість — кандидат на людський перегляд замість тихо прийнятого рішення. **Задум не справдився**, і це чесно заміряно: на двох запитах, які розійшлися між ідентичними прогонами, модель обидва рази поставила `high`. Поле лишається — воно дешеве й зрідка ловить справді хиткі кейси, — але покладатися на нього не можна. Подробиці в розділі про недетермінізм. |
| `mentioned_systems` | Google Ads, PlanFix, BigQuery, Meta, Slack — сигнал маршрутизації: за системою видно, яка команда володіє задачею. Витягується тим самим викликом, тобто безкоштовно. |
| `possible_duplicate_of` | У даних REQ-013 просить «той самий звіт по Google Ads, що Оля просила в понеділок» — це не нова задача, а доповнення до REQ-001. Такі зв'язки — головне джерело подвійної роботи в спільній черзі. Заповнюється **окремим проходом**: у порядковому виклику модель бачить рівно один запит і про інші не знає в принципі. |

Чого свідомо **не** додано: `is_actionable`. Його повністю покриває
`category: "поза скоупом"` разом із порожнім `requested_actions` — і REQ-008
(«дякую, все працює»), і REQ-012 (закупівля ноутбука) розкладаються без нього.
Кожне зайве поле — це токени в кожному запиті й ще одна поверхня, на якій модель
може помилитись.

## Що станеться, коли модель поверне сміття

Це не гіпотеза — на цьому будувалась уся обробка. Драбина знизу вгору:

1. **Обмеження на рівні API.** `response_mime_type: application/json` +
   `response_schema` — модель обмежена ще до генерації, вигадати назву категорії
   чи пропустити поле вона не може.
2. **Толерантний розбір.** Огорожі ` ```json `, проза навколо об'єкта —
   зрізаються.
3. **Нормалізація до валідації.** `"Автоматизація"` → `автоматизація`,
   `"HIGH "` → `high`, `"так"` → `true`, рядок замість списку → список із одного
   елемента, `"невідомо"` → `null`. Валідне-але-неохайне не має коштувати
   платного виклику.
4. **Строга валідація Pydantic**, включно з семантичними правилами, яких не
   виражає JSON-схема: прапорець уточнення зобов'язаний мати питання, і навпаки.
   Зайві поля заборонені — якщо модель дописала своє, вона імпровізує, і це
   сигнал, а не шум.
5. **Один repair-виклик.** Моделі повертається її ж відповідь і дослівний текст
   `ValidationError` — вона виправляє конкретне порушення, а не гадає.
   Кількість спроб — `TRIAGE_MAX_REPAIRS`, за замовчуванням 1: друга спроба
   рідко допомагає там, де не допомогла перша, і подвоює вартість.
6. **Запис зі статусом `failed`.** Рядок зберігається цілком, з оригінальним
   текстом і поясненням у `meta.error`, і окремою секцією потрапляє у звіт.
   **Прогін не падає, дані не зникають.**

Транспортні збої (429, 5xx, таймаут) обробляються принципово інакше: це
випадковість, яка лікується повтором того самого запиту. Витримка береться з
відповіді сервера, якщо він її назвав, інакше — експонента з джитером.
Плутати ці два класи помилок дорого: повторювати невалідний вивід безглуздо,
а «лагодити» промптом вичерпану квоту неможливо.

Перевірено тестами — `tests/test_extractor.py`, `tests/test_ratelimit.py`.
На живій моделі це не тестується: вона ламається тоді, коли їй заманеться, а не
коли ми запускаємо тести.

## Де рішення ламається

### Квота провайдера — найжорсткіше обмеження

Перший реальний прогін завершився тим, що 14 запитів із 18 впали з 429.
Причина не в паралельності: семафор обмежує *одночасність*, а квота рахує
запити *за хвилину*. Це різні речі, і перше не обмежує друге.

Далі з'ясувалося цікавіше: у `gemini-2.5-flash` безкоштовний тір — це
**5 запитів на хвилину і всього 20 на добу**. Тобто на цій моделі повний
прогін по 18 рядках можна зробити рівно один раз на день, і це не те, на чому
щось налагоджують.

Закрито двома речами:

- **обмежувач частоти** (`TRIAGE_RPM`) — обгортка над клієнтом, тому під ліміт
  потрапляють усі звернення, включно з repair-викликами й проходом по дублях;
- **витримка з відповіді сервера**. Gemini у відповіді на 429 прямо пише
  «retry in 28s»; наша експонента давала 4 секунди, тобто ще один 429.
  Тепер, якщо сервер назвав витримку, слухаємо його.

Плюс третє, вже про наш власний код: запобіжник, що зупиняє прогін після серії
збоїв, спершу рахував 429 за фатальну помилку й глушив обробку решти файлу.
Вичерпана квота — не зламаний конфіг, і тепер запобіжник реагує лише на справді
фатальне (невірний ключ, немає доступу до моделі).

Модель за замовчуванням — `gemini-3.5-flash-lite`: у неї ліміти вищі, і повний
файл проходить стабільно. При більших обсягах: платний тір, або Batch API, який
для несинхронної обробки інбоксу підходить краще за синхронні виклики.

### Обсяг

18 рядків — не навантаження. Що зламається на 10 000 на добу:

- **Немає стану.** Кожен прогін обробляє файл заново. Повторний запуск — це
  повторна оплата тих самих запитів. Потрібна ідемпотентність: хеш `raw_text` як
  ключ і кеш результатів.
- **Немає черги.** Один процес, один файл, усе в пам'яті. Реально потрібен
  воркер, який читає з черги й пише в БД, а не CLI поверх CSV.
- **Прохід по дублях не масштабується.** Зараз усі саммарі йдуть в один
  контекст — на тисячах запитів це не влізе. Правильно: ембединги + пошук
  найближчих сусідів, а LLM лише підтверджує кандидатів.
- **Обробка невідновлювана.** Прогін, обірваний на 900-му рядку, починається
  з нуля. Потрібен чекпоінт після кожного запису.

### Недетермінізм

`temperature: 0` прибирає варіативність з боку клієнта, але **не гарантує**
однаковий вивід: провайдер відтворюваності не обіцяє.

Це не теорія — я заміряв. Два прогони на **тому самому файлі, тій самій моделі
й тому самому промпті** (хеш промпту в маніфесті збігається) розійшлися на
двох запитах із вісімнадцяти:

| Запит | Прогін 1 | Прогін 2 |
|---|---|---|
| REQ-010 (згадки → дайджест → алерт) | `автоматизація` | `звіт/аналітика` |
| REQ-017 («терміново треба інтеграція слака з планфіксом») | `high` | `medium` |

**≈11% нестабільності**, і обидва випадки — рівно ті, де таксономія об'єктивно
на межі: REQ-010 має ознаки і автоматизації, і звітності; у REQ-017 є слово
«терміново», але немає дедлайну.

Найнеприємніше в цьому вимірі: **в обох прогонах модель поставила
`confidence: "high"`.** Тобто поле, яке я додав саме для того, щоб ловити
хиткі рішення, на цих кейсах не спрацювало — самозвітована впевненість не
корелює з фактичною стабільністю. Це вада самого підходу «спитати модель,
наскільки вона впевнена», а не одного промпту.

Що з цим реально працює, а що ні:

- ✅ `prompt_sha256` у маніфесті — розбіжність між прогонами одразу
  розділяється на «змінився промпт» і «модель поплила». Тут — друге.
- ✅ `reasoning` — видно, на чому будувалось кожне з двох рішень, і що обидва
  внутрішньо послідовні. Сперечатись можна з таксономією, не з моделлю.
- ✅ явні тай-брейкери в промпті — вони прибрали розкид із більшості запитів,
  але не з тих, де межа проходить по суті задачі.
- ❌ `confidence` як сигнал нестабільності — **не працює** в тому вигляді, як
  зроблено. Чесніший спосіб — прогнати запит N разів і взяти дисперсію
  відповідей; це коштує в N разів дорожче, і для межових кейсів воно того варте.

Чим **не** закрито взагалі: немає розміченого набору й метрики якості. Без них
«стало краще» — відчуття, а не факт. Це перше, що я зробив би далі, і саме
цей замір показує, чому воно перше.

### Вартість

Фактично з прогону на 18 запитах (`gemini-3.5-flash-lite`):

| | вхідні | вихідні | разом | оцінка на платному тірі |
|---|---:|---:|---:|---:|
| увесь файл | 33 529 | 3 001 | 36 530 | **$0.0176** |
| на один запит | ~1 863 | ~167 | ~2 030 | ~$0.001 |

На безкоштовному тірі фактична вартість — нуль; цифра вище показує, у що це
обійшлося б на платному.

Головне тут — **пропорція**: 92% токенів вхідні, і майже все це системний промпт
із таксономією, який однаковий для кожного запиту. Вартість визначається
промптом, а не текстом запиту. Звідси й економія: кешування системного
промпту дає найбільший ефект, скорочення промпту — ціною якості, відсів
очевидного до виклику (порожні тексти вже відсіюються).

**Модель коштує більше за все інше.** Той самий файл на `gemini-3.5-flash`:

| Модель | Час | Вихідні токени | Вартість | Різниця в результаті |
|---|---:|---:|---:|---|
| `gemini-3.5-flash-lite` (за замовчуванням) | 271 с | 3 001 | $0.018 | REQ-003 → `питання/консультація` |
| `gemini-3.5-flash` | 221 с | 23 727 | $0.264 | REQ-003 → `автоматизація` (правильніше) |

**У 15 разів дорожче** — і майже все це вихідні токени: у 3.5-flash увімкнене
внутрішнє «мислення», і вимкнути його не можна (`gemini-3.5-flash-lite` на
`thinking_budget=0` взагалі відповідає помилкою 400, тому прапорець
застосовується лише до моделей 2.5). За ці гроші купується одна виправлена
класифікація з вісімнадцяти — на цих даних воно того не варте, тому за
замовчуванням стоїть lite. На інших даних висновок може бути інший, і саме
для цього в маніфесті лежать токени: рішення перевіряється, а не вгадується.

`reasoning` і `confidence` теж коштують токени. Я вважаю їх вартими того; з цим
можна не погодитись — цифри вище дають порахувати.

Звідси й напрямки економії: кешування системного промпту (він незмінний і
становить основну частину входу), коротший промпт ціною якості, дешевша модель,
або відсів очевидного до LLM — порожні тексти вже відсіюються без виклику.
`reasoning` і `confidence` теж коштують токени; я вважаю їх вартими того, і в
цьому можна не погодитись — цифри вище дозволяють порахувати.

### Дані йдуть у зовнішній API

Тексти запитів разом із внутрішньою кухнею (назви систем, відділів, підрядників)
відправляються в Google. Для тестового завдання це нормально, для впровадження
потрібно щонайменше свідоме рішення: угода про обробку даних, або маскування
чутливого до відправки, або локальна модель. У коді цього немає, і робити вигляд,
що питання не існує, не варто.

### Дрібніше

- **Промпт-ін'єкція.** Текст запиту загорнутий у `<request_text>` із прямою
  вказівкою трактувати вміст як дані. Це знижує ризик, але не знімає: інбокс —
  недовірене джерело, і хтось може написати туди що завгодно.
- **Google Sheets** перезаписує аркуш цілком. Для знімка інбоксу це правильно,
  для журналу змін — ні.
- **Мова.** Промпт і таксономія українською. Запит англійською класифікується
  нормально (REQ-006), але вивід усе одно буде українською.

## Що зробив би далі

1. **Розмічений набір і метрика.** 50–100 запитів з еталонними мітками, скрипт
   заміру accuracy по категорії й пріоритету. Без цього будь-яка правка промпту —
   зміна наосліп. Замір нестабільності (вище) показує, наскільки це потрібно:
   11% відповідей плавають, і без еталона неможливо сказати, яка з двох версій
   правильна.
2. **Заміна самозвітованої впевненості на виміряну.** Прогнати межові запити
   N разів і взяти згоду між відповідями — це працює там, де `confidence` не
   спрацював. Дорожче в N разів, тому лише для кандидатів на межу.
3. **Ідемпотентність і кеш** за хешем `raw_text`. Дешево, а прибирає повторну
   оплату й робить прогони порівнюваними.
4. **Ембединги для дублів** замість одного контексту з усіма саммарі.
5. **Веб-хук замість CSV** — приймати запити зі Slack і Telegram напряму, писати
   в БД, віддавати чергу через API.
6. **Автоматичне заведення задач** для запитів із високою впевненістю, і
   черга на людський перегляд для решти — `confidence` для цього вже є.

## Розробка

```bash
uv sync              # залежності
uv run pytest -q     # 77 тестів, без мережі й без ключа
uv run ruff check .  # лінтер
```

```
src/triage/
├── models.py        # уся схема: вхід, контракт LLM, вихід, нормалізація
├── prompt.py        # промпти, правила таксономії, схема відповіді для API
├── extractor.py     # обробка одного запиту: драбина валідації та repair
├── pipeline.py      # читання CSV, паралельна обробка, запобіжник
├── dedupe.py        # другий прохід: дублі між запитами
├── report.py        # агрегати та три вихідні файли
├── cli.py           # точка входу
├── llm/             # base (контракт) · gemini · fake · ratelimit
└── integrations/    # telegram · sheets
```

Тести не ходять у мережу: усе через `FakeClient`, який або рахує за евристикою,
або віддає наперед задані відповіді, зокрема навмисно зіпсовані. CI ганяє лінтер,
тести й наскрізний прогін на `--provider fake` — без ключів і без бюджету.

Ключі беруться лише з оточення, `.env` у `.gitignore`.
